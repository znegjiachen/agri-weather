# 助农手 Agent 与通用模型对比

## 先说结论

我们比较的不是“哪个基座模型更聪明”，而是**通用模型直接回答**和**接入地块数据与工具的 Agent** 在真实农事问题上的差别。

结论：通用模型农业知识不差，但它不知道用户这块地的天气、生育期和预警；Agent 的价值在于把模型接到真实数据和可执行工具上。

## 对比对象

| 组别 | 模型 | 是否接入地块数据 | 是否可调用工具 |
|---|---|---|---|
| A. 问田 Agent | DeepSeek reasoner | 是 | 是，7 个农事工具 |
| B. 同模型裸答 | DeepSeek reasoner | 否 | 否 |
| C. 其他模型裸答 | Qwen2.5-72B-Instruct | 否 | 否 |

> B 组用于控制“基座模型相同”的变量；C 组用于看不同厂商通用模型的表现。B/C 都被要求“不知道就说明，不要编造”。

## 同一组问题的结果

测试地块：1 块水稻田，2026-05-01 播种，已进入收获期；天气为真实 Open-Meteo 数据。

| 问题 | A. 问田 Agent | B. 同模型裸答 | C. Qwen 裸答 |
|---|---|---|---|
| 我有几块地？种了什么？ | 直接列出 1 块地、水稻、播期、当前阶段 | 表示没有地块档案，要求用户提供 | 表示需要用户提供地块和作物信息 |
| 明天适合打药吗？ | 查到降雨 20.5mm、风速 20km/h、收获期，明确回答不适合 | 要求提供地点、天气、药剂和生育期，给通用判断原则 | 要求提供地点、天气、生育期和药剂 |
| 现在什么生长阶段？ | 判断为收获期，已种约 190 天，提示收获偏晚 | 要求提供播种日期、照片或田间特征 | 列出水稻生育期，要求用户补充信息 |
| 未来有冻害/大风吗？ | 查到低温和霜冻预警，结合收获期解释影响 | 说明无法判断天气，建议查看当地预报 | 说明无法提供天气，建议使用天气 App |
| 稻瘟病怎么防治？ | 先判断防治窗口已过，不建议此时打药，给当前阶段建议 | 给出完整通用防治方案，并声明需结合本地情况 | 给出较完整的通用防治方案 |

## 量化对照

| 指标 | A. 问田 Agent | B. 同模型裸答 | C. Qwen 裸答 |
|---|---|---|---|
| 需要地块数据的 4 个问题 | 4/4 给出基于真实数据的回答 | 0/4，均要求补充信息 | 0/4，均要求补充信息 |
| 编造天气/地块信息 | 无 | 无 | 无 |
| 通用知识题（稻瘟病） | 结合阶段与天气，偏保守 | 通用方案完整，较谨慎 | 通用方案完整，信息量最大 |
| 平均响应耗时 | 约 8.1s | 约 4.6s | 约 7.5s |
| 额外成本 | 工具调用 + 上下文 | 最低 | 中等 |

说明：B/C 没有编造，是因为我们在 system prompt 里明确要求“不知道就说明”；真实通用聊天产品不一定会这么保守。

## 优势在哪里

1. **数据落地**：能回答“我这块地明天能不能打药”，而不是“打药要注意天气”
2. **阶段约束**：知道作物已到收获期，不会给分蘖期才用的方案
3. **工具可验证**：每次回答能看到调用了哪个工具、参数和结果摘要
4. **权限边界**：只能查当前用户的地块，越权会被拒绝
5. **执行闭环**：通过 MCP 可以创建农事记录、种植季和提醒，写操作有确认与审计
6. **模型可替换**：基座模型通过 OpenAI 兼容配置切换，系统能力不绑定某一家

## 不能吹的地方

- 通用模型的农业知识面可能比我们内置知识库更广
- 本次只有 5 个问题、1 个模型版本、1 次运行，不能当作统计结论
- 没有做人工盲评，也没有真实农户现场对比
- C 组模型不是最新旗舰，且没有工具；这不是“模型智商排名”
- Agent 的延迟和 token 成本高于裸答

## 答辩话术

> 我们没有把“基座模型更强”当作优势，因为基座模型可以随时替换。我们的优势是系统层：把 DeepSeek 接到真实天气、地块、作物阶段、预警和农事工具上。对比里，同一个 DeepSeek 模型不接工具时只能让用户提供天气和播期；接入工具后能直接回答“明天不适合打药，因为降雨 20.5mm、风速 20km/h，而且已到收获期”。通用模型懂农业知识，但不知道用户这块地的情况，这就是差别。
